# Performance Analysis — ComposerRequireChecker

**Baseline**: ~19.14s on the `admin` project
**Date**: 2026-03-14
**Branch**: 4.23.x

---

## Top 10 Reasons for Slowness

### 1. Project source files are parsed TWICE

**File**: `src/ComposerRequireChecker/Cli/CheckCommand.php:131-162`

The main flow runs two separate AST passes on project files:

- **Pass 1** (L131-143): `LocateDefinedSymbolsFromASTRoots` — parses project + vendor + additional files to collect defined symbols.
- **Pass 2** (L153-162): `LocateUsedSymbolsFromASTRoots` — re-parses the same project + additional files to collect used symbols.

Both passes each create a `NodeTraverser` + `NameResolver` + Visitor. Files are re-read from disk and fully re-parsed. A single pass with both visitors would suffice for project files.

**Estimated impact**: ~3-5s (double I/O + double AST parsing of project files)

---

### 2. AST parsing of ALL vendor files (the heaviest cost)

**File**: `src/ComposerRequireChecker/ASTLocator/LocateASTFromFiles.php:31-54`

To discover symbols defined by dependencies, the tool parses with nikic/php-parser **every PHP file** of each direct dependency. On a Symfony project with 40+ dependencies, this means thousands of PHP files fully parsed into AST (lexer → parser → NodeTraverser + NameResolver).

AST parsing is the most CPU-intensive operation. An alternative would be to use the classmap/autoload generated by Composer (`vendor/composer/autoload_classmap.php`, `autoload_files.php`, etc.) which already list all symbols without any parsing.

**Estimated impact**: ~10-12s (the bulk of the time)

---

### 3. No cache between runs

**File**: No caching mechanism exists in the codebase.

Every run starts from scratch:
- Re-reading all PHP files from vendor/
- Full AST re-parsing
- Re-traversal of all directories
- Re-parsing of `installed.json`

A cache based on file timestamps or hashes would allow re-parsing only modified files. Vendor symbols rarely change between runs.

**Estimated impact**: potentially 90%+ of time eliminable on incremental runs

---

### 4. Recursive directory traversal per package, without sharing

**File**: `src/ComposerRequireChecker/FileLocator/LocateComposerPackageDirectDependenciesSourceFiles.php:38-44`

For each dependency, a **new instance** of `LocateComposerPackageSourceFiles` is created (L43), which itself creates a new `LocateAllFilesByExtension` (L151 of `LocateComposerPackageSourceFiles`) with a new `RecursiveDirectoryIterator` and recompiles the blacklist regex.

With 40+ packages, that's 40+ independent recursive traversals, 40+ regex compilations, 40+ instantiations.

**Estimated impact**: ~1-2s

---

### 5. `installed.json` and `composer.json` parsed multiple times

**Files**:
- `src/ComposerRequireChecker/Cli/CheckCommand.php:122` — `composer.json` parsed
- `src/ComposerRequireChecker/FileLocator/LocateComposerPackageDirectDependenciesSourceFiles.php:28` — `composer.json` re-parsed
- `src/ComposerRequireChecker/FileLocator/LocateComposerPackageDirectDependenciesSourceFiles.php:57` — `installed.json` parsed

`JsonLoader::getData()` reads the file from disk and parses it on every call, with no memoization. `installed.json` can be 100KB+ with all package metadata. Validation via `Psl\Type\shape()` adds a non-negligible cost on large JSON.

**Estimated impact**: ~0.3-0.5s

---

### 6. Expensive Psl type validation on JSON

**File**: `src/ComposerRequireChecker/JsonLoader.php:62-72`

`Json\typed()` with nested `Type\shape()` recursively validates each JSON field against the type schema. For `installed.json` which contains the full list of packages with their autoload, this structural validation is expensive.

The nested `Type\optional()`, `Type\union()`, `Type\dict()`, `Type\vec()` types (L77-99) generate a validation tree that traverses every JSON value.

**Estimated impact**: ~0.2-0.5s

---

### 7. `NameResolver` instantiated and run on every file

**Files**:
- `src/ComposerRequireChecker/DefinedSymbolsLocator/LocateDefinedSymbolsFromASTRoots.php:31`
- `src/ComposerRequireChecker/UsedSymbolsLocator/LocateUsedSymbolsFromASTRoots.php:30`

Each pass creates a `NameResolver` that visits **every node** of the AST to resolve fully qualified names. This is a second full tree traversal (in addition to the business visitor). For vendor files, only the `DefinedSymbolCollector` runs — but the `NameResolver` still does work proportional to the file size, not the number of defined symbols.

**Estimated impact**: ~2-3s (especially on large vendor files)

---

### 8. Expensive deduplication and sorting on large arrays

**Files**:
- `src/ComposerRequireChecker/DefinedSymbolsLocator/LocateDefinedSymbolsFromASTRoots.php:42`
- `src/ComposerRequireChecker/UsedSymbolsLocator/LocateUsedSymbolsFromASTRoots.php:41-45`

```php
// Defined symbols
return array_values(array_unique(array_merge([], ...$astSymbols)));

// Used symbols
$usedSymbols = array_unique(array_merge([], ...$astSymbols));
natcasesort($usedSymbols);
return array_values($usedSymbols);
```

With thousands of vendor files, `$astSymbols` contains thousands of sub-arrays. `array_merge([], ...)` merges them, `array_unique()` deduplicates (O(n log n)), then `natcasesort()` sorts again. The final `array_values()` creates yet another array.

**Estimated impact**: ~0.3-0.5s

---

### 9. No parallelization

**Overall architecture**

Everything is sequential:
1. Directory traversal → sequential
2. File reading → sequential
3. AST parsing → sequential
4. Node traversal → sequential

PHP is single-threaded by default, but solutions exist: `parallel`, `pcntl_fork`, or even preprocessing with workers to parse vendor files in parallel.

**Estimated impact**: total time could be divided by 2-4x with parallelism on vendor parsing

---

### 10. `Filesystem\is_file()` called on every file before reading

**File**: `src/ComposerRequireChecker/ASTLocator/LocateASTFromFiles.php:36`

```php
if (! Filesystem\is_file($path)) {
    continue;
}
```

For each PHP file found by the `RecursiveDirectoryIterator` (which already guarantees the file exists), an additional `stat()` call is made via `Filesystem\is_file()`. On thousands of files, these syscalls add up.

Additionally, `Type\non_empty_string()->coerce($file)` (L34) adds a type validation on each iteration.

**Estimated impact**: ~0.2-0.3s

## Impact Summary

| # | Cause | Estimated Impact |
|---|-------|-----------------|
| 1 | Double parsing of project files | 3-5s |
| 2 | Full AST parsing of all vendors | 10-12s |
| 3 | No cache between runs | (multiplier) |
| 4 | Non-shared recursive traversal | 1-2s |
| 5 | JSON parsed multiple times | 0.3-0.5s |
| 6 | Expensive Psl\Type validation | 0.2-0.5s |
| 7 | NameResolver on every file | 2-3s |
| 8 | Deduplication/sorting on large arrays | 0.3-0.5s |
| 9 | No parallelization | (multiplier) |
| 10 | Redundant stat() and coerce() | 0.2-0.3s |

> **Note**: Impacts overlap (AST parsing includes NameResolver, etc.). The total does not add up linearly.

## Priority Optimization Paths

1. **Use Composer classmaps** instead of AST parsing for vendor symbols → eliminates ~80% of the time
2. **Merge the two passes** into one with both visitors → eliminates double project parsing
3. **Add a file cache** based on timestamps → near-instant incremental runs
4. **Memoize JsonLoader** → avoid re-reading composer.json/installed.json
